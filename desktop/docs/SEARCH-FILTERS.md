# 检索精度：多关键词 AND + 时间/工作区过滤

上一轮让索引「新鲜」，这一轮让它「准」：能要求多个关键词同时命中，也能把范围收窄到最近几天或当前工作区。

## 一、能力

| 能力 | 行为 |
|---|---|
| 多关键词 | 空格分隔，**全部命中才算**（AND）。例：`登录 竞态` 只返回两个词都出现的会话 |
| 时间范围 | 全部 / 今天 / 7 天 / 30 天（`sinceDays`：0 / 1 / 7 / 30；**是回溯窗口，数字越大窗口越久**） |
| 工作区 | 「仅当前工作区」开关，按会话文件头里的 `cwd` 过滤（Windows 大小写不敏感、正斜杠归一化） |

界面：搜索框下方一行过滤按钮（`role=group` 名为「检索过滤」），点选即时生效。

## 二、实现要点

1. **FTS 路径**：所有关键词都 ≥3 个字符时，每个词包成短语，用空格连接（FTS5 中相邻短语即 AND），排序仍用 `bm25`（标题权重 4.0）；
2. **回退路径**：只要有一个词 <3 字符（trigram 处理不了），**整条查询**回退 `LIKE`，逐词 AND——不做「部分词走 FTS」的混合，避免语义不一致；
3. **工作区来源**：只读会话文件**第一行**（文件头的 `cwd`），不整文件读取；存的是归一化后的值，过滤就是等值比较；
4. **结构升级**：`SCHEMA_VERSION` 升到 2（新增 `cwd` 列）。版本不符时**直接丢弃缓存重建**——索引是纯缓存，重建比写迁移更可靠，且 `PRAGMA user_version` 让这一步自解释。

## 三、测试

会话索引单测从 7 条增到 **9 条**，新增两条直接对应本轮能力：

| 测试 | 覆盖 |
|---|---|
| `multi_term_query_requires_all_terms` | 两词都命中才算；只命中一个不算；含短词的查询回退 LIKE 后**仍然要求全部命中** |
| `filters_narrow_by_workspace_and_age` | 工作区过滤只留目标工作区；**把其中一份文件的 mtime 改到 10 天前**，验证最近 1 天的窗口确实排除了它、30 天窗口包含两者；未知工作区不命中 |

时间过滤那条用真实 `File::set_modified` 制造「旧文件」，不是靠 mock——所以它真的验证了 SQL 里的时间比较。

## 五、这轮的三次迭代（都在测试侧，不是产品 bug）

1. **单测断言写反**：`sinceDays` 是回溯窗口，数字越大覆盖越久，而我第一条断言期望「窗口越大越不命中」——把测试改成用真实 mtime 做排除验证才是对的；
2. **验收断言插错位置**：我把新断言插在原有断言的**中间**，导致后面那句读取命中的断言在「查询已被我改空」之后执行而超时。教训：**往既有的时序流程里插断言，要插在整段的末尾，并显式复位状态**；
3. **选择器歧义**：`getByRole('button', { name: '全部' })` 同时命中侧栏的「全部会话」切换与我的过滤按钮，触发 strict mode 违规。改成先取「检索过滤」分组再取按钮。

三次失败都在测试与选择器上；产品代码这轮只修了一处：把过滤参数从命令层透传到 `search_filtered`。

## 六、已知限制

1. **不支持 OR / NOT / 字段限定**（如「只在标题里搜」）；FTS5 的能力没有全部暴露给界面；
2. **短词回退是整表 LIKE 扫描**：几千个会话无感，数万级会有可感知延迟；
3. **过滤只作用于「内容匹配」**，侧栏上方的标题匹配不受时间/工作区影响（那部分是本地过滤，行为保持一致优先）；
4. **仍不支持跳转到命中位置**：点开会话是开头，不会滚动到那句话；
5. 关键词之间只按 AND 组合，没有「可选词」或相关度阈值。
