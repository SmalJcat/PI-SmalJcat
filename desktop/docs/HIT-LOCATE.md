# 命中位置跳转 + 会话内命中导航

内容检索原先只告诉你「在哪个会话」，现在补成完整的定位体验：**点开命中项 → 滚到那句话并高亮 → 可在多处命中之间前后跳转**。

## 一、为什么不用消息 id（有意的取舍）

最直觉的做法是把消息 id 存进索引按 id 滚动。探查后发现两处硬伤：

1. **会话文件里的 uuid 没有出现在渲染层**：`<Message>` 的 React key 是 `message._key`（前端 reducer 生成的客户端 key）；
2. 要让 id 通到底，得从 Pi 的 RPC 一路带到 DOM 并保证两侧对齐——**为一个滚动效果引入贯穿全链路的标识，性价比很低**。

改用**内容定位**：在已渲染的消息节点里找「文本包含全部查询词」的那些，滚动并高亮。**后端零改动**。

## 二、行为

| 场景 | 行为 |
|---|---|
| 点击内容命中 | 打开该会话，滚到**第一条**命中的消息并高亮 2.6 秒 |
| 命中不在最近 100 条里 | **自动展开更早的消息**（`显示更早的 N 条`）后重试，不需要用户先点一次 |
| 会话里有多处命中 | 右上角导航条显示 `第 N / M 处`，`↑`/`↓` 前后跳转（循环），`×` 关闭 |
| 历史异步到达 | **有界重试**（8 × 600ms ≈ 5 秒），不会在第一帧就判定「找不到」 |
| 确实找不到 | 明确提示（可能来自其它工作区或已被清理），而不是静默无反应 |
| 动效偏好 | 高亮用动画 + `outline`；`data-motion=off` 时动画被禁用但轮廓仍在，反馈不丢 |

两个容易踩的点都在实现里显式处理了：定位前必须 `setFollowing(false)`（否则「跟随最新」的自动滚底会立刻把定位冲掉）；导航时**重算命中集合**而不是缓存 DOM 节点（会话流式更新时节点会变）。

## 三、验证

```powershell
Set-Location desktop
npm test            # JS：96 项
npm run test:rust   # Rust：lib 99 项 + 集成测试（本功能后端零改动）
cargo clippy --all-targets --features test-fixture -- -D warnings   # clean
cargo fmt --check   # clean
npm run test:ui     # 真实 WebView2：39 项全过、渲染错误 0
```

两条验收项都断言**内容**而不是 class 存在：

| 验收项 | 断言 |
|---|---|
| 命中位置跳转 | 点击命中项后出现 `.message.hit-flash`，且**该消息文本包含查询短语** |
| 命中导航 | 导航条文本匹配 `第 N / M 处`；点「下一个/上一个命中」后仍有高亮；点关闭后导航条消失 |

## 四、已知限制

1. **文本匹配而非结构定位**：消息在渲染时被改写过（Markdown 结构变化、长文本折叠）可能匹配失败，此时给提示而不是乱滚；
2. **命中集合只在当前会话内**：跨会话的「下一个命中」没有做（要跨会话就得回到侧栏结果列表，那是另一种交互）；
3. **同一消息内多次出现只算一处**：以「消息」为粒度，不做消息内精确定位（也就没有词内高亮）；
4. **自动展开只在「最近 100 条之外还有消息」且首次未命中时触发一次**：如果命中在更早、且展开后仍未命中，会走「找不到」提示；
5. **要求全部查询词出现在同一条消息里**（与多关键词 AND 的检索语义一致），词分散在不同消息时不跳转。
