# 索引新鲜度：刚说完就能搜到

上一轮做完会话全文检索后，剩下的最大限制是：**索引只在启动时同步一次**，本次运行中新写的内容要等重启或手点刷新才搜得到。这轮把它抹平。

## 一、三层保证

| 层 | 做法 | 效果 |
|---|---|---|
| 搜索前 | `session-search` 先做 `sync_if_stale`：距上次同步超过 **3 秒**就先增量同步一次 | 刚聊完就能搜到，不需要手点刷新 |
| 一轮结束时 | 界面上 `agent_settled`（任务收尾）后触发一次后台同步 | 索引保持热状态，下次搜索几乎零等待 |
| 界面上可见 | 「内容匹配」标题旁显示 `索引 刚刚 / N 秒前 / N 分钟前` | 用户知道结果的时效，不用猜 |

**3 秒阈值是有意为之**：同步本身先做一次 stat 扫描，只对（mtime, size）变过的文件重建，成本很低，但没必要每次按键都扫一遍。

## 二、单测覆盖（这条才是真正区分"陈旧刷新"与"首次建索引"的）

`sync_if_stale_skips_fresh_and_refreshes_appended_content`：

1. 没有同步时间 → 必须同步；
2. 紧接着再问（阈值内）→ **跳过**，返回 `None`；
3. 会话**追加了新消息** → 即使不强制，`max_age` 到点后的同步也会把新内容带进索引（断言新句子可被搜到）。

## 三、验收

端到端断言改成了**不点「刷新索引」**：

```js
await page.waitForTimeout(3500);        // 刻意让索引进入陈旧状态（阈值 3 秒）
await searchBox.fill('中文流式输出');
await page.locator('.content-hit').first().waitFor({ timeout: 25000 });   // 自己刷新出来的命中
assert.equal(await page.locator('.content-age').count(), 1);              // 新鲜度提示可见
```

验收 **34 项全过、渲染错误 0**。

## 四、这轮踩到的两个坑（都是流程问题，不是功能问题）

1. **`--no-default-features` 的单测看不到 `desktop.rs`**：我改的 `session-search` 在 `desktop.rs` 里，而 `cargo test --no-default-features --lib` 不编译这个模块，所以类型错误（`spawn_blocking(...).await?` 解了一层 `Result`、实际是 `Result<Option<Value>>`，被当成 `Option<Value>` 用）在单测里完全没暴露；只有带 `desktop` 特性的 clippy 报了 `E0308`。

2. **绿色验收并不证明你的改动进了二进制**（这条更重要）：修好类型错误**之前**我跑过一次验收，结果是 `success=True / 34 项`——那时构建其实是失败的，跑的是**上一次遗留的可执行文件**；而且那个旧版本里"索引为空时惰性建索引"恰好也能让断言通过。教训：**验收绿了要回头看日志里的构建行与 `ui_exit`**，我在这一轮之后才把这条纳入检查（本次日志里能看到两次 `Compiling pi-desktop` + `Finished` 与 `ui_exit=0`）。

## 五、已知限制

1. **没有文件监听**：新鲜度靠"搜索前按阈值同步"，不是实时的；如果索引陈旧且用户一直不搜索，索引就不会更新（对单机使用足够，但不如 inotify/ReadDirectoryChangesW 精确）；
2. **每次搜索都有一次 stat 扫描**：几百到几千个会话文件是毫秒级，超大历史（数万文件）会有可感知延迟；后续可以给 stat 扫描加"仅扫最近 N 天目录"的剪枝；
3. **仍不支持"跳转到命中位置"**：点开命中是会话开头，不会滚动到那句话；
4. 会话在**外部工具**（直接用 Pi CLI）里被修改时，同样按 3 秒阈值在下一次搜索时才会被同步进来。
