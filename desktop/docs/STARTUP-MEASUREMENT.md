# 启动耗时：测量结论与口径（以及为什么不再优化）

> 结论先行：**进程内启动约 1.0–1.2 秒，其中 85–90% 是 WebView2 的启动成本，我们自己的代码合计约 150–170ms。不建议再投入优化启动。**

## 一、口径说明（这套数字到底测了什么）

计时零点在 `main()` 的**第一条语句**（`trace::mark_process_start()`），终点是前端上报首帧。因此：

| 计入 | 不计入 |
|---|---|
| Builder 与插件初始化 | **exe 加载与 DLL 解析**（发生在 main 之前） |
| 数据层（目录、偏好、任务记录、服务构建） | 操作系统的进程创建调度 |
| WebView2 进程启动到第一次回调 Rust | WebView2 运行时自身的冷/热状态差异 |
| 前端 JS 解析 + React 首帧 | 首帧之后的异步数据加载 |

报告的每一次返回都带一句 `scope` 说明，避免以后被误读成「完整冷启动」。

## 二、五次采样（同一份代码）

| 零点 | 总计 | 数据层 | 系统集成 | 命令通道（WebView2 就绪） | 前端就绪 |
|---|---|---|---|---|---|
| main | 1104ms | 91 | 92 | 1044 | 1104 |
| main | 1187ms | 109 | 110 | 1124 | 1187 |
| run() | 985ms | 76 | 76 | 924 | 985 |
| run() | 1055ms | 80 | 80 | 993 | 1055 |
| run() | 1745ms | — | — | — | — |（负载干扰的离群样本） |

两种零点之差约 10–30ms，就是 **Builder 与插件初始化**的成本。去掉离群样本后，总计集中在 **985–1187ms**，中位数约 1080ms，样本内波动约 ±60ms。

拆成阶段（相邻差值）：

| 阶段 | 耗时 | 占比 |
|---|---|---|
| Builder + 插件 + 数据层（含读取全部任务记录） | **~90–110ms** | ~9% |
| WebView2 启动到第一次回调 Rust | **~950–1020ms** | **~86%** |
| 前端 JS 解析 + React 首帧 | **~60ms** | ~5% |

## 三、按数据做过的优化，以及它的真实收益

在量出数字之前，我按常见直觉做了**面板按需加载**（React.lazy）：

| 指标 | 前 | 后 | 变化 |
|---|---|---|---|
| 主包 | 582.9 KB | **530.8 KB** | **−8.9%** |
| 主包（gzip） | 181.3 KB | **164.3 KB** | −9.4% |

体积收益是确定性的；但它能触及的只有那 **~60ms 的 JS 部分**，所以对启动的影响在**噪声之内**。**我不主张启动变快了**——采样波动（±60ms，另有 1745ms 的离群值）已经覆盖任何可能的收益。

构建还提示 `ReviewPanel.tsx` 被静态引用导致动态导入无效，我据此把 FilePreview/McpPanel 改回静态导入，**不留假懒加载**。

## 四、为什么不再优化

1. **86% 的时间不由我们掌控**：WebView2 的进程启动与运行时初始化是硬成本；
2. **我们自己的部分已经很小**：Rust ~100ms（含读全部任务记录）+ JS ~60ms；
3. **继续压缩 JS 的边际收益极低**：主包再小 10% 大约换来几毫秒，而测量噪声是几十毫秒；
4. **真要缩短，得改架构**（例如把首屏渲染从 WebView 换成原生、或预热 WebView 进程），代价与风险远超收益。

**所以：把启动数字留档为基线，后续若出现明显劣化（比如超过 2 秒）再回头看。**

## 五、留档机制

启动总计与阶段拆分**写进了验收项名称**，因此每次跑 `npm run test:ui` 都会把当时的启动数字记进 `artifacts/tauri-ui-result.json` —— 它是一条可回溯的时间序列，而不是一次性结论。

```powershell
Set-Location desktop
npm run test:ui
# 回执里会出现：启动耗时（总计 1104ms｜数据层 91 · 系统集成 92 · 命令通道 1044 · 前端就绪 1104）
```

## 六、已知缺口（关于测量本身）

1. **不含 main 之前的成本**（exe 加载、DLL 解析、进程创建）：要拿到需要平台 API（可能引入依赖），目前不做；
2. **每次验收只采一个样本**：中位数是靠多次运行拼出来的，单次数字受负载影响（已有 1745ms 的实证）；
3. **是 debug 构建**：Rust 侧那 ~100ms 在 release 下会更小，所以绝对数值只能用于**相对比较与回归发现**；
4. **`前端就绪` 之后仍有异步工作**（会话列表、文件树、索引同步），它们不阻塞首帧，但用户感知的「完全可用」比这个数字晚一些。
